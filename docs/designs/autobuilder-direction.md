## Context
The app optimizes Path of Exile 1 builds with the user's installed Path of Building (headless) as the engine,
plus a vault of what PoB lacks. A studio of 30 Claude agents builds it (tasks/ queue, GATES 1-4, Codex codes).
In flight: task 003 Phase A (A1 score FullDPS, A3 costs per resource, A2 unobtainable gems; A0 done; baseline
tests/golden.json, 21 tests). Planned: task 002 (compare with similar poe.ninja builds, gear tests).

Evidence (tasks/000, tasks/003, tests/golden.json):
- FR CombinedDPS, PoB skill part 1 (task 000): 5.27M (v1) → 6.40M (lost Militant Faith keystone re-taken)
  → 15.45M (v2, Cooldown Recovery breakpoint).
- FullDPS as saved (golden): v1 5,493,311.76; v2 15,621,685.11; v3 38,490,675.74; v4 57,001,026.47.
- v4 with the calibrated 4-of-6 projectile model: 38.06M FullDPS (draft, range 2-6 hits); with own shock 26%
  vs Pinnacle: 43.52M (draft).
The gains came from interaction knowledge and follow-up questions, not from tree search. PoB's number is not
the in-game number.

## Landscape (2026-10-22 search)
- poe-optimizer (github.com/alecrivet/poe-optimizer): greedy/genetic passive-tree search on PoB's engine.
- pob-mcp (pypi.org/project/pob-mcp): MCP server running PoB headless so an LLM gets real numbers.
- poe2-mcp: poe.ninja comparison, PoE2 only.
Nobody combines an interaction knowledge base, trade-offs with reasons, and quality gates. That is the edge.

## Vision

### 10x Check
A build coach that learns. Load any build (PoB file, pobb.in link, later poe.ninja character); detectors find
what an expert would; ask follow-ups in Claude Desktop and Claude runs PoB what-ifs with the vault's knowledge.
Every DPS shows PoB's number and the corrected number with a confidence label. The vault grows from sessions
and re-checks itself when PoB or the league changes.

### Platonic Ideal
"Make my FR build stronger for bosses." Three changes, each with DPS, EHP, cost and why, plus what to verify in
game. "Try Three Dragons" → interactions explained and tested. Nothing unlabeled: every number is PoB, a model
(draft or verified) or user-verified, with its source.

## Approach (D1)
C) Detectors + chat: every interaction check is a detector (vault note + engine module); an MCP server for
Claude Desktop exposes the engine; the GUI shows the same results. Chosen over B (GUI checks only) and A
(Phase A then stop).

## Detector contract (review #3)
- Input: an engine session (loaded build, scenario, per-build settings, Full DPS selection) + vault notes.
- Output: a list of Findings: `{id, detector, title, severity (info|suggestion|warning|rule-break), evidence
  (PoB values with keys, vault note links, sources with patch), confidence (PoB | model-draft | model-verified |
  user-verified), changes (objects accepted by optimize.apply_changes), dims (DPS/EHP/max hit/cost margin per
  resource, before → after), why (PoB modifier sources)}`.
- Vault kinds stay: Rules (constraints), Models (corrections), Gaps (PoB blind spots), Scenarios (fight
  assumptions). rules.py/models.py stay libraries. A detector is the runnable unit that uses them; each detector
  has one vault note (status, sources). The six existing audit checks are migrated to detectors after Phase A.
- Performance: detectors share one base evaluation per run; budget below.

## Corrections and confidence (E2, review #4, #8)
- Confidence labels (single definition): `PoB`, `model-draft`, `model-verified`, `user-verified`. Only the user
  promotes to verified (E1-min).
- Corrected number = PoB recalculated with all applicable models applied inside PoB (skill part / hit count
  first, then config effects such as own shock). Never multiplied by hand (GATE 1: hand-multiplying shock gave
  71.8M instead of PoB's 65.19M). No applicable model → corrected = PoB, label `PoB`. Label shown = lowest
  confidence among applied models.

## Engine sharing, GUI and MCP (review #6, #14)
- One engine owner: the existing local server (server.py, engine lock, one calculation at a time). The MCP server
  is a thin stdio process for Claude Desktop that calls the server's localhost API and starts it if it isn't
  running. No second PoB instance.
- Chat what-ifs and GUI audits write to the same per-build history (E7 storage), so the GUI shows chat results.
- Every call restores build state (existing hooks); writes only through the apply path with the server's
  path guard (Builds/AutoBuilder, never overwrite).
- Before building: evaluate reusing or forking pob-mcp (review #16; project research-and-reuse rule).

## Imports and network (E6, Q5, review #7, #19)
- pobb.in import first (fetch only `https://pobb.in/pob/<id>`, id pattern-checked); poe.ninja character import
  only after a probe confirms the endpoint (task 002 marks it unconfirmed).
- Untrusted input limits: code ≤ 256 KB, decompressed XML ≤ 4 MB (zlib bomb guard), XML parsed safely,
  imported builds saved to Builds/AutoBuilder/imports/ only.
- Per-source cache and rate limits: trade API (PoB's rate-limit rules), poe.ninja daily cache, pobb.in on
  explicit request only, wiki via API. Offline mode works on caches.

## Patch watch (E3, review #5)
- Triggers: PoB version change (launch.versionNumber), league change (trade API / poe.ninja index-state),
  manual run.
- Re-check per kind: Rules → re-run golden builds; Models → re-run their calibration builds; Gaps → re-check
  ModParser parse status; deny lists → re-check poe.ninja and wiki; notes not re-checkable → flagged
  "needs review".
- Golden tests stay exact within one PoB version; on a version change the suite reports "PoB version changed:
  N values moved" and re-pinning requires the user's sign-off (tests/pin_golden.py).

## Trade (E5, review #15, #18)

## Review decisions (sections 1-11, user, 2026-10-22) — override earlier text

  Chat what-if target ≤ 5 s when the chat engine is idle; if busy, MCP returns "busy" + a job id to poll

  change is a commit. Rollback = git revert.
- 2A Detector isolation: a failing detector reports "detector X failed: <reason>" in GUI and chat, is logged
  with context, and the other detectors keep running. No catch-all swallowing; named error per failure.
- 3A Local API: shared secret token (local file, userdata) required on every request from GUI and MCP, plus
  Host and Origin checks; anything else is refused.
- 3B Untrusted text: build notes, item names and other imported text are returned in marked untrusted fields;
  every write, upload or use of the login cookie needs the user's explicit confirmation in the GUI.
- 4A Stale facts: on a PoB version or league change, patch watch flips affected verified notes to
  "needs review"; numbers using them drop to the lower label until the user re-verifies.
- 5A One change vocabulary: tree convert, item replace (incl. flasks under Mageblood: replace, never
  switch off), config set, skill part, node allocate, gem level/swap and repath as change types in
  optimize.apply_changes / audit.lua, shared by detectors, MCP and GUI, each with tests.
- 6A Tests use recorded fixtures for pobb.in, poe.ninja and trade; a separate opt-in "live check" probes the
  real sites.
- 7A Cache PoB's power report per (build hash, config, PoB version); compute corrected numbers only for the
  suggestions actually shown; models.py support for the proposed Model kinds is P3 work; measure in P3.
- 8A Structured run log per run (detector timings, errors, external calls; never credentials) + a GUI
  diagnostics view.
- 9A Setup script: backs up Claude Desktop's config, registers the MCP server, asks first. Server lifecycle:
  single-instance lock, port check, MCP auto-starts the server, clean stop, no orphaned processes.
- 10A Split engine/audit.lua (759 lines) into hook modules by area before adding change types (800-line rule).
- 11A GUI shows PoB's number first, the corrected number beside it with its label.
