## Problem Statement
The app's three jobs are creating builds, optimizing builds and comparing a user build with a guide. All three need
to know why a choice works: why a notable is strong in one build and scenario and dead weight in another. Today every
generator run decides from zero. PoB scores each candidate node fresh (tree growth is 118-143 s of each tier
[measured: tasks/reports/021-eng-m1.md:23]; seeds take about 10 min [measured: tasks/reports/021-m3-session2.md:20]),
and nothing is kept between runs. The app can say "PoB says +X%", but not "strong for CoC crit, useless for freeze,
because ...". User (2026-10-25): "the app has to learn how build creation works, why in certain scenarios a notable
is good and in others bad. there needs to be a learning from this".

## What Makes This Cool
The app teaches itself through self-play. PoB is an exact simulator, so the app can test endless variations
overnight (take a notable out, put a different one in, swap a scenario) and learn from its own experiments, with
nobody else's data. Expert builds (the user's samples and public guides) add taste. The result is an app that
explains any notable in plain words, with the evidence behind it, and gets smarter with every run.

## Constraints
- PoB install and user builds are read-only. Self-play builds live in memory or under Builds\AutoBuilder\.
- Only one PoB engine is in memory at a time today (Lua heap about 170-220 MB per build,
  tasks/reports/021-m3-session2.md:19).
- Core features need no AI account (open-source audience). The model is a local file, runs on CPU, ships with the app.
- Runtime dependencies today: PyYAML only (requirements.txt). Any ML library is a new dependency.
- poe.ninja builds/profile endpoints are internal and "not available for third-party use" (poe.ninja/docs/api).
- PoE rounds down. Every displayed number comes from PoB or a vault note.

## Premises (agreed by the user, 2026-10-25)
1. PoB stays the judge: the model proposes and explains, but every number shown comes from PoB or the vault.
2. A notable's value is learned per context (the build's mechanics from the 027 interaction DB, mapping vs boss,
   tier), never as one global number.
3. Teachers: self-play (PoB-tested variations) plus expert builds (the user's samples and pobb.in guides).
   poe.ninja builds data only with their permission.
4. Every learned pro/con cites its evidence: PoB delta, modifier source, and how many builds it was seen in. When data
   is thin, the app says "not enough evidence".
5. The model ships inside the app, runs on CPU and needs no AI account.

## Approaches Considered
- A) Evidence table (aggregated self-play stats per notable x context): smallest, but it can't generalize to unseen
  builds. This is B's data layer.
- B) Trained surrogate: CHOSEN.
- C) Imitation of experts (learn which notables guides take): rejected. The data is small and it copies guide habits.

## Recommended Approach: B, trained surrogate
```
 seeds / samples / pobb.in guides
            |
            v
  SELF-PLAY RUNNER (background, one engine) ----> EVIDENCE STORE (append-only records)
  for build b, scenario s:                         {choice, context features, scenario, tier,
    remove / add / swap choice c                    dDPS, dEHP, dCost, PoB modifier source,
    PoB calc -> delta                               build id, PoB version, league}
            |                                                  |
            v                                                  v
  EXPERT ABLATION: for each node in a              TRAINER (offline): gradient-boosted trees
  sample/guide build, remove it, PoB delta          per target (dDPS%, dEHP%) from context
                                                    features -> model file + attributions
                                                               |
            +--------------------------------------------------+
            v
  USES: (1) "Why this notable" panel: learned pro/con + evidence count, PoB number for THIS build
        (2) later: rank tree candidates (PoB checks top N) -> faster generator
        (3) later: guide compare explains each difference in the user's context
```
- Delta definition (tree nodes): REMOVE = deallocate the node plus the nodes PoB orphans with it; ADD = allocate the
  node via PoB's shortest path; SWAP = remove A, add B for the same points. Each record stores dDPS% and dEHP% vs the
  unchanged build, the points moved, and the per-point values. Targets v1: dDPS%, dEHP% (dCost later).
- Context diversity: 3 seeds are few contexts, so self-play also varies the context itself: scenario
  (mapping/boss), tier, configs, skill and ascendancy variants, and the user's samples. Guides add more once cleared
  (Open Question 3).
- Context features: 027 interaction tags the build uses (crit, CoC, freeze, ...), damage types, ascendancy, scenario
  (mapping/boss), tier, key stat levels (crit chance, life/ES pool), allocated keystones.
- Pros/cons start as attribution HYPOTHESES ("strong because the build uses crit + CoC"). A reason is shown only
  after a counterfactual PoB test confirms it: remove or flip the named context (crit, scenario) and re-measure.
  Otherwise the panel says "measured, reason not confirmed".
- What the panel shows (for any choice: node, gem, support, item): the PoB-measured delta for THIS build (computed live) plus a learned label
  (strong / weak / neutral in this context) with its evidence count. Predicted numbers are never shown as numbers.
  They only rank and label, marked "learned".
- Staleness: the model file carries the PoB version and league it was trained on. On a mismatch the panel says
  "model from PoB x.y, retrain". A context outside the training range shows "not enough evidence".
- Fallback features if 027's engine phase slips: PoB modDB stats (crit chance, damage types, keystones, ailments).
- First visible win (user Q2): the "Why this notable" panel for every node of a build.

## Accepted scope additions (CEO review, user 2026-10-25)
- E1 Gems and items too (supports, uniques), not only notables. Delta per choice type:
  - gem: swap the active or support gem in its group, keeping the level and quality the build has (hand-set counts
    kept; a new gem gets the same level and quality, capped by obtainability);
  - support: remove from its links, or replace it with another support in the same socket;
  - item: replace the slot with the candidate (unique or target-stat rare), keeping other slots; jewels in a radius
    are tested by the slot, not the node.
  Each type gets its own spike timing (a gem swap is a full recalc).
- E2 Corrections are training signal and absorb task 016. Record fields: source = self_play | expert_build |
  correction, weight (correction 5x, expert 2x, self-play 1x [initial, tuned on the held-out check]), and the user's
  note. The change is always re-tested in PoB. If PoB disagrees with the user, PoB's number wins, the record is kept
  with the disagreement flagged, and the app asks whether a missing config or mechanic explains it (failure mode 8:
  this can be a vault gap). In the held-out check, corrections stay with their build's split.
- E3 "Learn overnight" button: self-play in the background with progress, a stop button and a "what it learned"
  summary (new records, labels that changed). Engine rule: one engine queue. Interactive requests (generate, audit,
  panel) take priority, and self-play pauses at the next record boundary and resumes afterwards. No second engine.
- Deferred: E4 community-shared records (hosting, privacy, bad-data rules first).

## Milestones (each with its own gate)
- M1 (D2, user 2026-10-25 "Evidence first"): evidence store + self-play runner + "Why this notable" panel with the
  exact PoB delta and 027 interaction-based reasons. No trained model yet.
- M2 gems/supports/items: per-type deltas and spike, then the panel covers every choice type.
- M3 corrections as signals (E2).
- M4 "Learn overnight" button with the engine queue (E3).
- M5 trained surrogate (approach B): only after records cover several independent build lineages and the model beats
  the evidence table, rule retrieval and nearest-neighbour baselines on untouched archetypes (thresholds preregistered).
- M6 (user 2026-10-25, goals check): the learned knowledge steers the generator. It ranks tree candidates during tree
  growth and PoB checks only the top N, so generated builds improve as the app learns and the generator gets faster.
  Ranking source = the best learned knowledge available (M1 evidence table first, the M5 model once it passes); can
  start after M1. Gate: on the 3 seeds, builds at least as good (FullDPS, TotalEHP) as without ranking, in less time.
If the M1 spike forces "notables only", M2 runs only after its own spike passes. E1 is not dropped, just gated.

## Open Questions
1. ML dependency: add scikit-learn / LightGBM (wheels for Python 3.14?) or a small pure-numpy GBDT. Decide in
   /plan-eng-review.
2. Self-play throughput: the time of one PoB delta calc is not measured. 0.1 s per calc is [estimated], which gives
   about 100k-300k records per night [estimated]. Spike first.
3. pobb.in guide intake: fetching single user-provided links is already done (engine/guide_routes.py). Bulk
   collection of guides needs a source and terms check.
4. Where records live: a gitignored data store (records are machine output) vs the vault (human-verified knowledge).
   The proposal is data store for records and vault for promoted, verified rules.
5. Model versioning against PoB/league changes: retrain or invalidate when the PoB version or league changes.
6. Task 016 is absorbed by E2 (closed). Task 027 engine phase supplies the context features (dependency, see Next Steps).

## Codex outside-review fixes (2026-10-25)
- Premise 1 wording: PoB is exact only for the given config; config gaps and unmodelled mechanics are flagged
  (vault Gaps), never learned as truth.
- Marginal attribution: ADD = (path + node) - (path only); REMOVE = node alone when no orphans, else recorded as a
  "bundle" and not attributed to the node.
- Exploration: 20% of self-play choices random/control, so the runner never only confirms its own ranking.
- Label is multi-target: DPS, EHP, plus reservation/mana margin, caps, cost and points. The panel shows the trade-offs,
  not one "good".
- Evidence counts are shown as independent build lineages, not raw mutation counts. Held-out splits group by lineage
  (descendants, corrections and near-duplicates stay together).
- Corrections are separate signals: factual (PoB-checkable), preference, or mechanic-gap report. They are not
  weights on one target (replaces E2's 5x/2x/1x).

## Gates
- Spike go/no-go: GO if self-play reaches 10,000 or more records per night on one engine [threshold, set before the
  spike]. NO-GO -> restrict to notables only and drop small nodes; if still too slow, ship A (evidence table) on the
  measured records.
- B over A (M5): the trained model is kept only if it beats A's per-context averages on the held-out check. Otherwise A
  ships, and B waits for more contexts.
- Held-out rule: leave one build out (train on all but one seed/sample, test on the one left out), split by build id.
- Data rights: the shipped model is trained only on self-play and the user's own samples. Third-party guides are used
  only after a terms/licence check.

## Success Criteria
- M1: for every tree node of the 3 seed builds, the panel shows a learned pro/con with an evidence count and the PoB delta for
  this build, or "not enough evidence".
- Held-out check: the model's predicted sign and rough size of a notable's dDPS%/dEHP% matches PoB on builds it was
  not trained on (threshold set after the first baseline).
- Contrast check: at least one notable that the model correctly rates strong in one seed and weak in another, with
  the reason confirmed by the counterfactual PoB test (e.g. a crit notable in EK CoC vs Worb).
- M2: the same for every gem, support and item of the 3 seeds.
- M3: a correction becomes a record, is re-tested in PoB, and a PoB disagreement is shown, not hidden.
- M4: self-play runs while the app is idle; an interactive request is served within one record's time, and stop
  leaves a consistent store.
- No AI account needed; the model file loads offline.

## Distribution Plan
Ships in the repo with the app: the trained model file plus the trainer script. Users can retrain locally from their
own self-play runs. The existing local server (server.py) and gui/index.html serve the panel. No new channel.

## What I noticed about how you think
- You framed the whole product around one idea: "why in certain scenarios a notable is good and in others bad".
  That is a context problem, not a ranking problem, and it shaped every premise.
- You picked the trained model over the cheaper table, so you want it to generalize to builds it hasn't seen.
- You chose "Why this notable" as the first win over speed, so you put explanation before optimization.
